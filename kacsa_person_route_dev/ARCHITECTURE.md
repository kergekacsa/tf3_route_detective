# Architecture

How the mod is built, which rules its code follows, and what the game does that the type definitions do not show. The player-facing behaviour is in `README.md` and the terms in `CONTEXT.md`.

## Folders

| Folder | Content |
|---|---|
| `staging_area\kacsa_person_route\` | The mod as the game loads and uploads it: `mod.json`, `strings.json`, `image_00.jpg`, `content\`, `_metadata\`. It holds no other file, because an upload carries the whole folder and the platform allows only essential files with lowercase names. |
| `staging_area\kacsa_person_route_dev\` | The documents, the tests, the Teal configuration (`tlconfig.lua`, `all_def.tl`), and the git folder of the mod. |

The repository has its work tree at `staging_area` (`core.worktree`), and `.git\info\exclude` leaves out everything but these two folders. So `git` MUST run in `kacsa_person_route_dev`: in the mod folder it finds the repository of the Road & Rail Upgrade Brush, which excludes both folders in its own `.git\info\exclude`.

## Mod layout

All paths are under `staging_area\kacsa_person_route\content\person_route\`.

| Path | Role |
|---|---|
| `route_card.res.lua` | Registers the card at the extension point of the vanilla person window: a generic resource of type `react-plugin ::SimPersonEowExtensionPoint` with `filePath` and `order` 50. The vanilla cards have the orders 20 (Locations), 30 (Happiness), and 40 (Current Route). |
| `route_card.script.tl` | The card: the plugin recipe, the permanent row, the expandable part with its two blocks, and the map tool that draws the options the player switched on. It renders the data of the modules below; its only engine reads are the edge geometries for the drawing. |
| `route_card.css.lua` | The stylesheet of the card: the thick divider between the blocks (`prc-divider-thick`), the space under a block title (`prc-gap`), the indent of the town line and of the places of a leg (`prc-indent`), the centred row of buttons (`prc-actions`), the dot of an option (`prc-bullet`), the colour of the arrows of the current leg (`prc-current`), and the bold fonts of the leg the person is on (`prc-bold`) and of a block title (`prc-header`). The game loads a `.css.lua` file of a mod by its name. |
| `route_state.tl` | Reads the trip of one person from the engine into plain data: the phase, the current leg, the towns with their names, and the edges of the path the person follows now. |
| `route_compare.tl` | The options of a trip: walk, car, and the routes by lines, each with its legs, its time, and its length. The option the game chose is built from the leg the game exposes (the path the person walks or drives, the line of the current ride) and the estimate of the legs before and after it. Every leg carries its edges for the map. |
| `route_lines.tl` | The search for routes by lines. It builds a network of the stations (a ride on a line from a stop to any later stop, a walk between two stations in reach of each other), finds the best route from every station to the nearest target station, and hands out the best route per first line and the route from a given station. It also wraps the pathfinder of the game, finds the street nodes of a building and of a station, and gives the edges a leg runs over. |
| `prc_types.d.tl` | The global types of the mod. Every global name carries the prefix `Prc`. |

Outside `content\`: `mod.json`, `strings.json` (12 languages besides English, keys with the prefix `prc_`), `tlconfig.lua` and `all_def.tl` for the type check, and `tests\`.

## Conventions

- The mod id is `kacsa_person_route`. It does not change.
- The mod MUST be independent: no mod dependency, no change to the vanilla cards.
- Every file path, text key, recipe name, and global type MUST be unique across mods: `person_route/`, `prc_*`, `Prc*`.
- Engine reads live in `route_state.tl` and `route_compare.tl`. The card calls `api.engine` only to read the geometry of an edge it draws. The two modules return plain Lua data (numbers, strings, booleans, entity ids, edge ids), so the comparison of the react state is cheap and the tests can check the data.
- The options are computed once per leg of a trip. The timer of the card checks every two seconds whether the origin, the target, the phase, the line, the leaving stop, or the refresh counter changed, and returns the old result otherwise. `route_compare.compare` writes one log line with the tag `[PersonRoute]` and its duration in milliseconds, because it asks the pathfinder for every leg of every option.
- `getStation2edgesMap` returns a table with every station and every edge in its catchment area (185 stations with about 340 edges each in the test map), and each call builds that table again. One computation of the options took 95 to 120 ms for a driver and 447 ms for a person with four options while every station lookup fetched the map. `route_lines.batch` keeps the map, the stations of every catchable, the street nodes of a station, and the network of the lines for one computation.
- A car path of the game (`MovePath.path.edges`) holds the whole drive from the origin to the target, also when the car is already on its way.
- A text that exists in the game with the same English words (`Home`, `Shop`, `Work`, `Walk`, `Car`, `Lines`, `Line`, `Yes`, `No`) uses the game's key and has no entry in `strings.json`.
- A comment in the code MUST state only a contract, an invariant, a unit, or a constraint that holds now.

## Game API

- The plugin loader reads every generic resource of type `react-plugin <extension point id>`, resolves `filePath` with `util.useFn`, and sorts by `order` (`gui/main/react.lua`, `getPlugins`). The extension point id is `<mod id of the owner>::<name>`, and the mod id of the base game is empty, so the person window's id is `::SimPersonEowExtensionPoint`. `RegisterPluginRecipe` needs only a table with that id; the mod does not require the vanilla script, because a second `RegisterExtensionPoint` with the same name is refused.
- `filePath` has the form `<mod id>::/<path without .tl>@<field>`. The field is a recipe in the table the script returns.
- A recipe that the extension point mounts receives `SimPersonEow.SimPersonWidgetPluginParams`: `entityId`, `gameCtx`, `showCalloutOnRightSide`, `setCollapsibleExpanded`, `getCollapsibleExpanded`, and the vanilla `state` of the window.
- Engine reads happen in the callback of `engine_react_util.useStepState` (every step) or `useStepStateTimer` (interval in seconds). The vanilla cards use the same pattern.
- The result of the game's pathfinder reaches a script only as one `PathFactoryOutput` (one path, one cost, one move mode, at most two line sections, `api\tealdef\api\type.d.tl`), and the component that carries it, `SimEntityNeedsPath`, has no `ComponentType` entry. So neither the alternatives nor the cost of the chosen route are readable.
- The route the game chose is readable through the leg components: `SimEntityAtTerminal` (line, boarding stop, alighting stop, arrival time, vehicle), `SimEntityAtVehicle` (line, stops, vehicle), `SimPersonAtVehicle.expectedArrivalTime`, `SimEntityMoving` (line, stops, `partialPath`, `expectedArrivalTime`). A driving person carries `LAND_VEHICLE` and `MOVE_PATH`; a walking person carries `MODEL_PERSON`.
- `SimPerson.moveModes` and `SimPerson.travelTimes` have one entry per destination, indexed by land use type plus one (the vanilla table of a building reads `moveModes[type + 1]`). The unit of `travelTimes` is not documented. The index of `travelTimes` and its unit are inferred and not yet confirmed in the game.
- `SimPerson.travelTimes` read `{0, 0, 0}` in the game for every person checked (driving, waiting, riding), while `moveModes` held real values. The card shows neither.
- The entries of `MovePath.path.edges` are objects with the fields `edgeId` and `dir`, not pairs as the type definition declares. `route_state.edgeOf` reads an entry as a pair first and as such an object second.
- The entries of `ModelPerson.path.edges` have `range` (`edgeId`, `params`, `dir`) or `link`. A person who waits at a terminal or rides a vehicle keeps the `MODEL_PERSON` component with the walking path of the leg before, so `route_state.currentPath` returns no path in those phases.
- A town building carries `PERSON_CAPACITY` itself (`TownBuilding.personCapacity` is the building entity). Its `personNodes` hold one node of the building's own transport network (`entity` = the building, `index` 2), and its `vehicleNodes` are empty. `findPathNodeToNode` between the person nodes of two buildings returns an empty list, for `PERSON` and for `CAR`.
- `findPathNodeToNode` works between nodes of street edges: with the first node and the last node of a car path of the game it returned a path of the same edge count. Its result entries are real pairs (`entry[1]` is the edge id, `entry[2]` the direction). `Edge.transportModes` is indexed by the number of the transport mode. `api.engine.util.pathfinding.EdgeIdDirAndLength` does not exist at run time, so `findPath` with starting edges is not usable.
- `getTargetsByLandUse` returns a userdata with the member `residential`, a table of two target datas (729 and 828 entries in the test map). A target data has `entries` and `edges`. An entry names a building with `entity`, and `edgeWalk` and `edgeDrive` are ranges of positions in `edges` (first position 0, end excluded), not edge ids as the type definition suggests. An item of `edges` is an edge position with `edgeId` and `param`. The walk edge of a building is an edge of the building's own transport network. The entries hold shops and workplaces; a home has no entry. The mod does not use it.
- `api.engine.getComponent` accepts the number of a component type. The run-time enum has more names than the type definition (`VEHICLE_ORDER`, `MODEL_PERSON_IDLE`). A person carried no component without a name, so the component with the planned route of the game (`SimEntityNeedsPath`) is not on a person who moves or waits.
- The path of a line between two stops is not exposed. `route_lines.legPath` asks the pathfinder for the path between `Terminal.vehicleNodeId` of the two stops, section by section, with the transport modes of `Line.vehicleInfo.transportModes`. The terminal of a stop is `Station.terminals[stop.terminal + 1]`.
- The class `card-children-separator` of the game draws a thin line inside a content card. The arrows around the current leg are `::/gui/entity_window/icons/arrow_head_right.tga` and `arrow_head_left.tga`, and the dot of an option is `::/gui/main/icons/circle.tga`. Both are grey-scale images; the stylesheet property `color` on an `ImageView` tints one, and `colorDefault.Warning` is the yellow of the game. The eye icons are `::/gui/line_vehicle_mgmt/icons/symbol_eye.tga` (a crossed eye) and `::/gui/menu/icons/mod_management/mod-invisible.tga` (an open eye).
- The catchables of a station are building entities. `getStation2stationsAndDistancesMap` gives the stations in walking reach of a station; the line estimate uses it for a transfer and reads the distance as metres.
- `TransportVehicle.sectionTimes` has one entry per stop of the line, with values like 60 to 100 for a train line, which fits seconds. `getMaxFrequency` gave 0.0027 for a line with one vehicle, an interval of 375 s.
- A trip can use several lines: persons waited at stations that are not in the catchment area of their origin, and their line did not reach a station near the target. The components of a person name only the line of the current leg. The legs after it are not readable, so the card shows the route `route_lines.tl` finds from the station where the person leaves the current line.
- A station can be in the catchment area of a building and have no line stop.
- The game sets the font weight only in the font classes of `gui/main/font_scaling.css.lua` (`!font-scale-body` sets `Regular`). A text with `font-scale-body` and a second class that sets `fontWeight` was bold in one run of the game and regular in the next, with the same rules. So a bold text of the card carries one font class of the mod that sets weight and size, and no font class of the game.
- The game sends the event `OnModifyPathfinding` of `SimPersonSystem` to game scripts. Its parameter holds `town2lineCostFactor`, a factor per town on the cost of lines. The vanilla `towns.script.tl` sets it for a town with a marketing campaign, and a mod can set it for every town. A GUI script cannot read the factor. So the game chooses by a cost, and the times of the card do not explain a choice by themselves.
- `PersonCapacity.pathfindingPreference` of a building has `destinationWeight` and `disallowedMoveModes`. Both town buildings checked had the weight 1 and no disallowed move mode.
- Engine objects list their member names in `__members`, and the global `toString` of the game (`base/serialize.lua`) prints an object with them. The entity debug panel of the game uses both.
- `SimPerson.lastNonResType` is a `LandUseType`; the vanilla window uses it as the destination index of the origin of a trip home, so `RESIDENTIAL` is 0, `COMMERCIAL` 1, `INDUSTRIAL` 2.
- Game time (`GameTime.gameTime`, `arrivalTime`, `expectedArrivalTime`, `lastDestinationUpdate`) is in milliseconds. `api.util.formatSeconds` takes seconds. Speeds are in m/s.
- A line stop names a station group and a station index; the station entity is `StationGroup.stations[station + 1]`. The vanilla happiness log resolves a stop the same way.
- `api.engine.util.line.getMaxFrequency` returns vehicles per second; the vanilla line util computes the interval as `1 / frequency` and treats a value under 0.0001 as no vehicle.
- `TransportVehicle.sectionTimes` holds one value per section between two stops of the line. Its unit is not documented; the estimate treats it as seconds. The vanilla GUI does not read it.
- `catchmentAreaSystem.getStationCatchables(station, false)` lists the entities with a `PersonCapacity` in the catchment area of the station. A town building names its capacity entity in `TownBuilding.personCapacity`; an industry carries `PERSON_CAPACITY` itself. The estimate checks both.
- `api.engine.util.pathfinding.findPathNodeToNode(startNodes, destinationNodes, transportModes)` returns the edges of a path. The vanilla GUI does not call it, so the estimate runs it inside `pcall` and shows the message when it fails. The person nodes and vehicle nodes of a building come from `PersonCapacity.personNodes` and `vehicleNodes`.
- An edge of the transport network (`TransportNetwork.edges[index + 1]`) has `geometry.length`, `speedLimit`, and `curveSpeedLimit`. The estimate uses the lower of the two limits.
- Drawing on the map goes through the world-layer action of a tool: `builtin.ActionDescriptor` with `builtin.EdgeRenderable` (one per recipe, the engine asserts on more) and `builtin.LineViewer` as children. A window owns its action through `params.setActionFn`, and a plugin card has no access to it, so the card pushes a tool of its own (`react.RegisterTool`, `gameCtx.toolStack:get():getApi().push(tool, key, param, true)`) and pops it when no path is shown or the card unmounts. The action of the tool rebuilds the HUD icon manager and the entity selector of the default action (`gui/main/selector_react_util.tl`, `makeDefaultSelectorAction`) with the default HUD filter, because that function offers one custom child only.
- Pushing a tool shelves the tool of the entity windows, and its shelve handler hides the active window (`gui/entity_window/view_manager.tl`, `EntityDetailsTool.shelve`). The window id is `temp.view.entity_<entity>`, so the tool shows the window again with `api.gui.byId.setVisible` in its push handler and in the mount of its action. When the tool is popped, the window tool unshelves and shows the window itself.
- An edge of the transport network carries its `EdgeGeometry`, and `builtin.type.EdgeRenderable.Edge.new(geometry)` draws it. A car path is `MovePath.path.edges`; a walking path is `ModelPerson.path.edges`, whose entries are edge ranges or links; the card draws the whole edge of each range.
- `builtin.type.LineVisualization` with a line entity makes the line viewer draw the whole line in its colour. The vehicle, line, and station windows use it the same way.
- A component and the values inside it are views of engine data. An edge id of a path that the card kept in its state read as `nil` in a later step. Code that keeps a path across steps MUST copy each edge id into plain Lua data (`entity`, `index`) in the step that reads it. `route_state.tl` and `route_compare.tl` do this, and they skip an edge id that is not readable. When a walking path has entries and none is readable, `route_state.tl` writes one log line with the tag `[PersonRoute]` per game session.
- The transport network of a town building has three nodes and two edges for persons, and no edge of it joins a street edge: `findPathNodeToNode` finds no path from a node of a building to a node of a street. The run-time enum has a component type `TP_NET_LINK`, which fits a separate link between the two networks. The pathfinder does find a path on foot between the person nodes of two street edges.
- The run-time enum has the component type `PARCEL` (number 70), which the type definition does not list. `TownBuilding.parcels` names parcel entities, and `Parcel.streetSegment` is the street edge entity of the parcel. `route_lines.buildingNodes` takes the nodes of the edges of that street that allow the transport mode as the ends of a walk or a drive. An industry has no parcels.
- `getStation2edgesMap()[station]` lists pairs of an edge id and a distance. `route_lines.stationNodes` takes the nearest edge that belongs to a street (the entity has `BASE_EDGE`) and allows persons as the end of a walk at a station.
- The run-time enum also has `SIM_ENTITY_NEEDS_PATH` (number 75), the component with the path request and result of the game. A person who moves, waits, or rides does not carry it, and `getEntitiesWithComponent` refuses it (`Cannot loop over this component type`). So the route the game plans is not readable at any time.
- The destination targets of `getTargetsByLandUse` are not used by the code any more.
- A cell of a `builtin.Row` MUST NOT be a layout (`BoxLayout`, `TableLayout`): the engine stops the GUI step with `TableLayout cell must not be a Layout`. A text view, a registered recipe, or a `builtin.Component` with the layout inside is accepted. The type definitions do not show this rule.
- Teal: `enum` is a keyword, so the enums of the game are read as `api.type["enum"].MoveMode`. The GUI type definitions (`Builtin`, `React`, `ContentCard`, `SimPersonEow`, and the others) ship in `base\tealdef\`, so `tl check` works with the two definition folders of the game and the `content` folder of the mod.
- A loop variable named `_` hides the translation function `_`. The code uses `__` for an unused loop variable, as the vanilla scripts do.
